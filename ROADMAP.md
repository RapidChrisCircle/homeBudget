# Roadmap

Planned work for homeBudget, with a status against each task so an interrupted session can be picked up later without re-deriving the reasoning behind it.

The three documents at the repo root divide cleanly:

| File | Answers |
|---|---|
| [`README.md`](README.md) | How the app works **today** |
| [`CHANGELOG.md`](CHANGELOG.md) | What **shipped**, and when |
| `ROADMAP.md` (this file) | What's **next**, and how far it got |

Written against **v0.22.1** (`961b5ee`). The review this roadmap came from is condensed in [Appendix A](#appendix-a--review-findings) — every task links back to the finding that justifies it, so the *why* stays attached to the *what*.

## How to use this file

- **Pick any task.** They're grouped in rough value-per-effort order, but each carries its own context and none depends on another unless it says so. Tier order is a recommendation, not a sequence.
- **Mark `[~]` when you start**, and add a one-line note saying where you got to and which files you already touched. That note is the entire point of this file — it is what a cold session reads to resume rather than restart.
- **Mark `[x]` only when merged and green**: both test suites pass, `npx oxlint src` and `npm run build` are clean. Record the version that shipped it beside the tick.
- **Ship it the repo's way**: a `CHANGELOG.md` entry and a `VERSION` bump in the same change (see README's [Versioning](README.md#versioning) section), and a README update if user-visible behaviour changed.
- **Leave completed tasks in place** rather than deleting them — the notes are the history of *why* something ended up the way it did, which the changelog entry alone rarely captures.
- **Task IDs** (`T1.1`, `T2.3`…) are stable. Reference them in commit messages so the connection survives even if this file is reorganised.

### Status legend

| Mark | Meaning |
|---|---|

## Scope boundaries

Decided, not overlooked. **Do not propose these again** without the boundary being revisited explicitly:

- **Authentication — out of scope.** This is a local-LAN-only application by explicit decision: no login, no shared password, no reverse-proxy auth layer. The deployment publishes the UI on a host port for a household network and that is the intended model.
- **Multi-currency** — a single-currency household app; every amount is one currency and no conversion exists anywhere.
- **Receipt/document attachments** — a file store, its backups and its lifecycle are a disproportionate amount of machinery for the value here.
- **Tax-deduction flagging** — jurisdiction-specific and better served by exporting to whatever the household's accountant actually uses (see [T1.4](#t14--csvjson-export)).
- **Multi-user / shared households** — no user model exists, and adding one touches every endpoint. A single shared instance on the LAN is the model.
- **Bank/open-banking sync** — already covered in README's [Categorization](README.md#categorization) section: the commercial enrichment APIs are paid per-transaction and require sending spending history to a third party, and there is no credible free or offline equivalent.

## Tier 1 — highest value per unit of work

Self-contained, independently shippable, and each one is felt in daily use.

### T1.1 — Manual transaction entry

- **Status:** `[x]` — shipped in **0.23.0**.
- **Why:** [Finding 1](#finding-1). Import is the only data path, so cash spending, a transaction not yet on a statement, or a reimbursement simply cannot be recorded. This caps the app's usefulness mid-month, exactly when a budget should be steering decisions.
- **What shipped:** `POST /transactions` and `PUT /transactions/{id}` (`backend/app/api/transactions.py`), `Transaction.is_manual` (migration `a762ac78878d_add_is_manual_to_transactions`), a new **Add a Transaction** card on `/transactions` (`AddTransactionForm.jsx`) and an **Edit** action on a manual row's Details disclosure (`EditManualTransactionForm.jsx`), plus a "manual" badge on the row.
- **How the constraints below were actually resolved:**
  - **Balance**: computed, not invented - the account's current latest balance (via the existing `services/ledger.account_balance`) plus the new row's own signed amount. This is only correct if the new row *becomes* the latest transaction, so both create and edit **require** the transaction to be dated on or after the account's other latest one - rejected with a 422 naming that date otherwise. Documented in README's new "Manual transactions" section and in `create_transaction`'s own docstring.
  - **Duplicate-on-later-import**: documented as a known caveat rather than solved - a manual row's computed balance will never match a later real statement's own reported balance, so import's duplicate key can't recognize them as the same row. Reconciling is a manual step (delete whichever is redundant). Revisit if this proves painful in practice.
  - **Exactly one of debit/credit**: enforced the same way import enforces it, but the two API fields are deliberately *positive* dollar amounts (a Money out/Money in choice) rather than already-signed values, so a user typing "$45 for groceries" never has to remember to type `-45` - the sign convention is applied once, server-side (`_signed_amount_and_type`).
  - **Cash account companion**: no new machinery needed - `POST /accounts` already creates an account with any account number, `CASH` included.
  - **Editing scope**: deliberately narrower than "every field" - the account itself can't be changed on an existing manual row (that's a balance recomputation on two accounts' sequences at once; delete-and-recreate covers it with far less risk). Every other field can.
- **Tests:** 26 backend (`tests/test_manual_transactions.py`) + 21 frontend (`AddTransactionForm.test.jsx`, `EditManualTransactionForm.test.jsx`, plus 6 new cases in `TransactionsPage.test.jsx`) - full suites (581 backend, 640 frontend) green, lint and build clean.

### T1.2 — Filtered-total summary strip on the ledger

- **Status:** `[x]` — shipped in **0.23.1**.
- **Why:** [Finding 10](#finding-10). `components/Pagination.jsx` reports `(N total)` — a **count**. Filter the ledger to "Groceries, July" and the app will not tell you what it adds up to, which is the single most likely reason someone filtered in the first place.
- **What shipped:** `services/ledger.ledger_totals` (money in/out/net over whatever query object is passed - reused as-is for the plain view) and `transaction_group_totals` (the identical total over the grouped view's own filters, factored through a shared `_grouped_filters` helper so the two can't drift). Both `GET /transactions` and `GET /transactions/groups` gained `total_in`/`total_out`/`net_total`. A new `.ledger-totals` strip renders them between the toolbar and the table in `TransactionsPage.jsx`, reading the plain fetch's own totals regardless of whether Group by merchant is on - the two are proven to always agree for the same filters, so there's no separate group-totals state to keep in sync.
- **A design call worth recording**: totals sum each matching row's own signed debit/credit - the exact figure already shown per row - not a per-allocation split figure. A split transaction matched through only ONE of its several category allocations still contributes its full amount, deliberately consistent with what the ledger already displays for that row rather than the stricter per-category slice `services/allocations.py` gives every report instead. Documented prominently in `ledger_totals`' own docstring so it reads as a decision, not a bug, if revisited.
- **Tests:** 6 new unit tests in `test_ledger.py` (whole-set-not-one-page, sign split, filter-respecting, empty-set, split full-amount, grouped-matches-plain) + 3 HTTP-level tests in `test_transactions.py` + 3 frontend tests in `TransactionsPage.test.jsx`. Full suites (590 backend, 643 frontend) green, lint and build clean.

### T1.3 — Statement continuity / coverage check

- **Status:** `[x]` — shipped in **0.23.2**.
- **Why:** [Finding 4](#finding-4). Import is the only data path, so a missing statement period silently understates every total and nothing notices. This app can **prove** coverage rather than assume it, because it already stores the bank's own running balance.
- **What shipped:** `backend/app/services/coverage.py`'s `account_coverage_gaps(db, account_id)`, a pairwise walk over one account's own transactions ordered by `(transaction_date, id)` checking `balance[n] == balance[n-1] + debit[n] + credit[n]` between adjacent DISTINCT dates only (see below). `GET /accounts/{id}/coverage` (`AccountCoverageResponse`) surfaces it, and a new **Statement Coverage** card on `/accounts/:id` lists any detected gaps with their date range, expected vs. actual balance, and the discrepancy - or a plain reassurance when there are none. Left for [T2.4](#t24--alerts-feed) to also surface as an alert - this task only builds the per-account check and its own page.
- **How the caveats were actually resolved:**
  - **Same-day tolerance**: the pairwise walk simply **skips** any adjacent pair sharing the same `transaction_date` - the check only ever fires between the *last* row of one date and the *first* row of the next distinct one. A real missing-statement gap almost always spans whole days or weeks, so this removes an entire class of false positive (same-day file order not matching import id order) at no real cost to detection.
  - **A brand-new account's first transaction**: falls out for free from the pairwise-zip implementation - the first row is never a "current" being checked against a "previous", so it's never flagged.
  - **Grouped accounts**: never even enters the picture - the function is scoped to one `account_id` and never reads another account's rows at all, so a group's handover between members can't be mistaken for a gap without any group-aware code needing to exist.
- **Tests:** 9 unit tests (`test_coverage.py`, covering all four acceptance criteria plus multi-gap and duplicate/out-of-order cases) + 3 HTTP-level tests in `test_accounts.py` + 3 frontend tests in `AccountDetailPage.test.jsx`. Full suites (602 backend, 646 frontend) green, lint and build clean.

### T1.4 — CSV/JSON export

- **Status:** `[x]` — shipped in **0.23.3**.
- **Why:** [Finding 8](#finding-8). Years of financial history with no way out, behind a Watchtower auto-updater that runs Alembic migrations unattended (see README's own warning in [QNAP Deployment](README.md#qnap-deployment)). Export is both the backup path and the exit.
- **What shipped:** `services/export.py` with two functions - `ledger_csv(query)` (filtered CSV) and `database_snapshot(db)` (whole-database JSON) - and two new endpoints, `GET /transactions/export` (ledger CSV, on the ledger's filter bar) and `GET /export/database` (JSON, on `/accounts`). Both are plain `<a href>` download links on the frontend, not calls through the `api` client, so the browser handles the save itself from `Content-Disposition`. `list_transactions`' own filter validation was factored into a shared `_validated_ledger_query` so the export can never accept a filter combination the ledger view itself would reject.
- **How the round-trip criterion was actually resolved:** documented as a deliberate non-goal rather than engineered around. The CSV's header doesn't match the built-in bank layout (`services/csv_formats.py` matches a layout by *exact* header string) and carries Category/Note/split information no bank format has a column for - a categorized, split-aware export is what makes it useful outside the app, and a second, re-importable bank-shaped export was never asked for and would be a different, more limited file. The JSON backup has no restore endpoint for the same reason: true point-in-time recovery is a Postgres-level restore, which is out of scope for this app to reimplement.
- **A correctness subtlety worth recording**: `database_snapshot`'s per-table dumps mostly validate straight off ORM rows via each schema's own `from_attributes=True` (matching exactly what e.g. `list_csv_formats` already does) - except `savings_goals`, whose `GoalResponse` fields (`current_amount`, `percent`, ...) are computed by `services/goals.goal_progress`, not stored on `SavingsGoal` itself. That one is assembled by hand, mirroring `api/goals.py`'s own private `_serialize_goal` rather than importing it (which would invert this codebase's api → services layering). A test pins that the export's own goal serialization is byte-identical to `GET /goals`.
- **Tests:** 16 tests in `test_export.py` (CSV shape/filtering/pagination-defeat/split-flattening/shared-validation, JSON table completeness/parity-with-live-endpoints/archived-inclusion/empty-database) + 2 frontend tests for the ledger's Export CSV link (`TransactionsPage.test.jsx`) + 1 for the Accounts backup link (`AccountsPage.test.jsx`). Full suites (618 backend, 649 frontend) green, lint and build clean.

### T1.5 — Savings rate and runway tiles

- **Status:** `[x]` — shipped in **0.23.4**.
- **Why:** [Finding 7](#finding-7). The two headline numbers households actually track, and every input already exists.
- **What shipped:** `services/net_worth.liquid_assets()` (new - Everyday + Savings balances, sign-and-group-aware exactly like `net_worth_now`) and two new `dashboard_kpis()` fields, `savings_rate` (`net_saved / total_income`) and `runway_months` (`liquid_assets() / avg_per_month`). Both new `stat_tile` metrics (`savings_rate`, `runway_months`) appear in the Add Widget list automatically - `STAT_TILE_METRICS` is derived from `METRIC_META`'s own keys, so no registry change was needed. `StatTile` gained a `formatValue` prop (defaulting to the existing currency formatter) so a ratio renders as a percentage (`formatPercent`) or a month count (`formatMonths`, new in `utils/format.js`) instead of a dollar figure.
- **The exact definitions used**: savings_rate as specified. Runway divides CURRENT liquid assets by THIS WINDOW's average monthly spend - "at this spend rate, how long would today's cash last", not a projection (that's `services/forecast.py`'s own job, not duplicated here).
- **How the zero-denominator cases were resolved**: both are `None`, not `0` or an error - `savings_rate` when the window had no income at all (a household living off savings has no "rate" to report), `runway_months` when the window had no expenses to divide by. A real answer of exactly zero (expenses exist, liquid assets don't) is left as `0`, distinct from both.
- **Tests:** 12 backend (6 `liquid_assets` cases in `test_net_worth.py` incl. group-contributor and inverted-sign; 6 `dashboard_kpis` cases in `test_dashboard_metrics.py` incl. both zero-denominator paths and a negative rate) + 2 HTTP-level + 10 frontend (`StatTileWidget.test.jsx`, `StatTile.test.jsx`, `format.test.js`). Full suites (632 backend, 662 frontend) green, lint and build clean.

### T1.6 — Global search / command palette

- **Status:** `[x]` — shipped in **0.23.5**. **Tier 1 is now complete.**
- **Why:** [Finding 11](#finding-11). Nine destinations and thousands of transactions, with navigation by scanning a flat link row. The largest perceived-speed gain available in the UI.
- **What shipped:** `frontend/src/components/CommandPalette.jsx`, mounted once in `App.jsx` outside the routed `<Routes>` tree (so it survives navigation rather than remounting and losing its fetched data every route change). `Ctrl+K`/`Cmd+K` opens it from any page; Escape or a click outside closes it; arrow keys move the selection; Enter or a click activates it. Results are grouped (Pages, Categories, Accounts, Merchants) using ARIA `role="group"` with an `aria-label`, inside one `role="listbox"`, with `aria-activedescendant` kept in sync on the input for proper combobox semantics.
- **How "already in memory" was actually resolved:** pages genuinely are (`pageRegistry.jsx`, a static import). Categories and accounts are **not** globally cached anywhere in the app - every page fetches its own copy independently - so the roadmap's assumption didn't quite hold. Resolved by having the palette fetch both itself, but **lazily**: only on the first time it's opened, cached in its own state for the rest of the session, rather than adding two unconditional requests to every single page load for a feature most sessions never open. Merchants have no "list them all" endpoint at all, so they're searched live and debounced (200ms, matching this app's existing no-per-keystroke-request convention) through `GET /transactions/groups?search=`, the identical endpoint the ledger's own Group by merchant view already uses.
- **Tests:** 17 in `CommandPalette.test.jsx` (open/close via every mechanism, each result kind and its navigation target via the `LocationProbe` pattern `TrendsPage.test.jsx` established, lazy single-fetch caching, debounced merchant search via fake timers, keyboard navigation, empty-query and no-matches states) + confirmed `App.test.jsx`'s existing 8 unaffected by the new mount. Full suites (632 backend, 679 frontend) green, lint and build clean.

## Tier 2 — the features that change what the app *is*

### T2.1 — Budget carryover and sinking funds

- **Status:** `[x]` — shipped in **0.24.0**.
- **Why:** [Finding 2](#finding-2). The biggest conceptual gap between a spending *reporter* and a budgeting *tool*. Today, $100/month toward $1,200 of annual car registration reads as eleven quiet months and one catastrophic one.
- **What shipped:** an opt-in **"Roll unspent budget into next month"** checkbox on a category's budget field (`/categories`), backed by `Category.rolls_over` + `rollover_start_year`/`rollover_start_month` (migration `b891fd23e6a1`). `services/budgets.rollover_history`/`rollover_available` walk the accumulation forward one month at a time from the recorded start; `CategoryPeriodTotal.available_amount` (new, `None` for every non-rollover category) carries the result into `/reports` and `/budgets`, and `difference` now reads against it when present. Monthly Budgets (`/categories`) gained an **Available** column and a "rolls over" badge; `/reports`' Budget vs Actual table gained the same badge inline, since its Difference column is silently computed against that figure, not the bare Budget number beside it.
- **How the open design questions were actually resolved:**
  - **Epoch**: not category creation, not a user-supplied date — accumulation starts the month `rolls_over` is switched on, stamped automatically on the False→True transition and cleared back to `None` on True→False (so re-enabling later starts a fresh accumulation rather than resurrecting a stale one). Walking a category's entire lifetime history on every read was rejected as both unbounded and not what "I just turned this on" actually means.
  - **A new choke point, not a rewrite of `effective_budget`**: `effective_budget()` still answers exactly what it always has — this month's own nominal figure — and every existing caller (`/trends`, `copy_budgets`, `/budgets` itself) is completely unaffected. `rollover_available()` is a second, single-purpose resolver for the genuinely different question "including carry-in, what's actually available," the same pattern `net_worth.signed_balance` already sets living beside `ledger` rather than inside it.
  - **The `/goals` envelope connection in the original design note was deliberately NOT built**: on closer inspection the two answer different questions rather than duplicating one. A savings goal's envelope is a manually-tracked target ledger ("$5,000 toward a car"); budget rollover is an automatic accumulation of ordinary monthly *budget headroom* feeding the existing reports/dashboard budget-vs-actual figures. Forcing them to share a mechanism would have meant either goals gaining an auto-accumulating monthly budget it doesn't want, or rollover gaining a target-amount/progress concept it doesn't need. Recorded here rather than silently dropped, since the original note explicitly asked for it.
  - **Performance**: bounded by construction, not caching - the walk only ever runs from a category's own `rollover_start`, which by definition began the day this feature could first apply, not from all of history. `category_totals_for_period()` runs the walk only for categories that are actually flagged `rolls_over` (a small, opt-in second query pass), leaving the main per-month aggregate every category hits completely untouched.
  - **Known scope limit, not a bug**: `/trends`' multi-month grid (`category_grid`) still shows the nominal, non-accumulated budget line for a rollover category. It has no "difference"/over-under concept at all (unlike `/reports` and `/budgets`), so extending it wasn't required by this task's acceptance criteria and was left out to keep the change bounded.
- **Tests:** 9 unit tests for `rollover_history`/`rollover_available` (`test_budgets.py` — accumulation, deficit carry-forward, a no-own-budget month, a net-refund month, the exact car-registration scenario from the roadmap) + 2 for `category_totals_for_period`'s `available_amount`/`difference` (`test_reporting.py`) + 1 HTTP-level (`test_budgets_api.py`) + 6 for the create/update stamp-and-clear transitions (`test_categories.py`) + 4 frontend (`CategoriesPage.test.jsx`: checkbox submission, edit prefill, Available column + badge, dash-when-not-rollover) + 2 frontend (`ReportsPage.test.jsx`: badge shown/not-shown). Full suites (650 backend, 685 frontend) green, lint and build clean.

### T2.2 — Pay-period budgeting

- **Status:** `[x]` — shipped in **0.25.0**.
- **Why:** [Finding 3](#finding-3). The preset is a Queensland household, where fortnightly pay is the norm, and three months a year contain three pay cycles — which a calendar-monthly budget mis-states in both directions.
- **What shipped:** following the roadmap's own suggestion, shipped as an alternative fortnightly **view** over the existing monthly budgets, not a second, independently-edited budget period. A single-row `PaySchedule.anchor_date` (migration `c4d72f8e91a3`, a known payday) is the one anchor every fortnight boundary is computed from (`services/pay_periods.py`); a **Pay Period Budgeting** card on `/categories`, below Monthly Budgets, lets a household set that payday once and then navigate Previous/Next between fortnights, seeing each category's standing monthly budget rescaled to a fortnightly pace against that period's real spending. `GET`/`PUT /api/pay-schedule` and `GET /api/pay-periods` back it; the latter answers `{"configured": false}` rather than 404ing when no payday is set yet.
- **How the design questions were actually resolved:**
  - **Overrides deliberately not consulted**: pacing reads only `Category.budget_amount` (the standing figure), never a monthly `CategoryBudget` override. A fortnight can straddle two different calendar months, each potentially carrying its own override, and there is no principled rule for which one a 14-day window should defer to - resolving that arbitrarily would be worse than plainly not attempting it, so this is documented as a limitation in both the service module and the README, not silently guessed.
  - **The budget period itself was NOT made configurable** - the roadmap correctly flagged this as the most invasive possible approach ("a period" is hard-coded to "a calendar month" throughout reporting/trends/budgets/dashboard), and a purely additive fortnightly pacing view answers the actual Finding (a household paid fortnightly can't see its true pace) without risking any of that existing surface area.
  - **T2.1 overlap**: pacing does NOT reuse T2.1's rollover accumulation - a rollover category's *available* figure is a calendar-month concept (carry-in from the previous *month*), and a fortnight boundary rarely lines up with a month boundary, so there is no clean way to ask "how much of this fortnight's carry-in is available" without inventing a third, hybrid accumulation model nobody asked for. Pacing uses the plain standing amount for every category, rollover or not; recorded here as a considered choice rather than a missed connection.
  - **Bounds correctness**, the acceptance criterion: `pay_period_bounds()` counts whole 14-day steps via integer floor division on `(reference - anchor).days`, which is exactly as correct for a date long before the anchor as long after it, and never special-cases January 1st or a month edge - so a three-pay month (verified with a fixture anchor that puts periods on Apr 23/May 7/May 21 2026) and a year boundary (Dec 25 2025 anchor spanning into Jan 2026) both fall out of the same one code path, not two.
- **Tests:** 20 backend (`test_pay_periods.py` - bounds before/at/after the anchor, the three-pay-month and year-boundary acceptance scenarios, `fortnightly_pace`, anchor get/set/upsert, category totals scoped to the window and excluding transfers, summary, and the HTTP endpoints incl. the not-configured shape) + 1 for the JSON backup gaining `pay_schedule` (`test_export.py`) + 5 frontend (`CategoriesPage.test.jsx`: the set-payday form, submission, the configured view's range/table/summary, Previous/Next navigation, an over-pace badge). Full suites (671 backend, 690 frontend) green, lint and build clean.

### T2.3 — Transfer matching

- **Status:** `[x]` — shipped in **0.26.0**.
- **Why:** [Finding 5](#finding-5). Both legs are excluded from reports by kind, but nothing pairs them — so one leg mis-categorized silently inflates spending *and* income.
- **What shipped:** `backend/app/services/transfer_matching.py` (`transfer_candidates`, `unmatched_transfer_legs`), `GET /api/transfers`, and a **Transfer Matching** card on `/transactions` (`TransferMatchingCard.jsx`, self-fetching so the already-large `TransactionsPage.jsx` didn't need to own another piece of state). Shows only the two cases worth attention — a matched pair whose categorization doesn't agree it's a transfer, and a transfer-categorized leg with no counterpart — the same "only the problems" posture `NeedsAttentionWidget` already uses for over-budget categories.
- **How the design questions were actually resolved:**
  - **Narration deliberately NOT used**, despite the original note pointing at `services/narration.py`'s merchant-key machinery: a real bank transfer is usually worded differently by each side's own statement ("Transfer to XXXX1234" vs. "Transfer from XXXX5678"), unlike a recurring merchant where the narration genuinely repeats. Requiring narration agreement would miss exactly the case this exists to catch, so matching is amount + date proximity only, cross-account.
  - **A candidate pair is reported regardless of current categorization** - not just among transactions already marked `kind == "transfer"` - specifically so a mis-categorized leg (an expense that should have been a transfer) is exactly as visible as a correctly-tagged one; restricting the search to transfer-only rows would have made this feature blind to its own headline case.
  - **Greedy, amount-grouped matching**: transactions are grouped by exact absolute amount first (cheap even on a large ledger, since only same-amount rows are ever compared), then each debit claims its nearest unclaimed, cross-account, opposite-signed credit within the window - so a transaction is never claimed by two different pairs.
  - **Surfacing in the alerts feed** (the roadmap's original "Where") is left to [T2.4](#t24--alerts-feed), which lists unmatched transfers as one of its own inputs - `GET /api/transfers` is the shared source both the ledger card and the alerts feed read from independently, matching this app's "every widget reads its own data live" convention rather than threading shared state between the two.
- **Tests:** 14 backend (`test_transfer_matching.py` - the three acceptance scenarios verbatim, plus both-categorized/mismatched-categorization, split-transaction and no-account exclusions, at-most-one-pair, and the two HTTP endpoint shapes) + 5 frontend (`TransferMatchingCard.test.jsx` - reassurance state, a fully-categorized match staying hidden, a mismatched match shown, an unmatched leg shown, an error state). Full suites (685 backend, 695 frontend) green, lint and build clean.

### T2.4 — Alerts feed

- **Status:** `[x]` — shipped in **0.27.0**.
- **Why:** [Finding 6](#finding-6). Over-budget categories, subscription price rises, a bill that didn't arrive, an account not imported in weeks, coverage gaps ([T1.3](#t13--statement-continuity--coverage-check)), unmatched transfers ([T2.3](#t23--transfer-matching)) — all already computed or cheap to compute, none surfaced unless you visit the right page.
- **What shipped:** `services/alerts.py` assembles from four EXISTING computations - `reporting.category_totals_for_period`/`budget_lines` for over-budget, `recurring.detect_series` for price changes and missed/stopped, `coverage.account_coverage_gaps` per account, `transfer_matching.unmatched_transfer_legs` - no new detection logic anywhere. `GET /api/alerts`, an **Alerts** page (`/alerts`) listing every current alert with a Dismiss button, and an "Alerts (N)" badge on the nav link.
- **How the dismissal design was actually resolved:** deliberately NOT one new system for every kind. A recurring-sourced alert (missed/stopped, price change) dismisses through the **existing** `POST /recurring/dismissals` verbatim - `/recurring`'s own Dismiss button already does exactly this, keyed on `(account_id, narration_key)`, and `detect_series()`'s own default already excludes a dismissed series, so there is nothing new to track for that half of the feed. Only the three kinds with no dismissal concept yet (over-budget, coverage gap, unmatched transfer) share one new, generic, key-based `AlertDismissal` table - one row per dismissed fact, keyed on a deterministic string built from that fact's own identity (e.g. `over_budget:{category_id}:{year}:{month}`, `coverage_gap:{account_id}:{before_date}:{after_date}`, `unmatched_transfer:{transaction_id}`) rather than a surrogate row id, since there is no persisted "alert" to reference - only the recomputed fact. A *different* occurrence of the same kind of problem therefore gets a different key and is never silently suppressed by an old dismissal of something else.
- **Scope note**: "an account not imported in weeks" (mentioned in Finding 6's own review text, though never listed as one of this task's four `Where` sources) was deliberately left out - there is no concept of an account being intentionally closed/inactive anywhere in the schema, so a fixed staleness threshold couldn't tell "importing has lapsed" apart from "this account is done" without guessing, which conflicts with this app's "surface it, don't guess" posture. Revisit only if a closed/archived account concept is ever added.
- **Tests:** 14 backend (`test_alerts.py` - one appear/dismiss/reappear-on-restore round trip per signal kind, cross-key non-interference, dismissal idempotency, and the HTTP endpoints incl. the count-matches-the-feed acceptance criterion) + 8 frontend (`AlertsPage.test.jsx` - empty state, listing, the deep link, both dismiss paths, an error state, and kind labels) + 2 frontend (`App.test.jsx` - the nav badge showing a count and showing none). ### T2.5 — Navigation, mobile ledger, chart tooltips

- **Status:** `[x]` — shipped in **0.28.0**. **Tier 2 is now complete.**
- **Why:** [Findings 9, 13, 14](#appendix-a--review-findings). The three UI changes with the broadest reach; can be done independently but share a release well.
- **What shipped:**
  - **Grouped navigation** — `pageRegistry.jsx` entries gained a `group` field (`Money`/`Plan`/`Insight`/`Setup`) and a fixed `PAGE_GROUP_ORDER`; `App.jsx` clusters the nav accordingly. A page with no `group` (Home, and the new Alerts link from [T2.4](#t24--alerts-feed)) renders as its own standalone link, exactly like Home already did — both are cross-cutting, not a content area, so grouping them WITH the content they point at would be the wrong hierarchy. Stacks into full-width rows below 900px, the same breakpoint the widget grid already collapses at.
  - **Responsive ledger tables** — the ledger's plain and grouped-by-merchant tables both opt into a new `.responsive-table` (`App.css`) that turns into one card per row below 700px: the standard accessible technique of visually-hiding `<thead>` (clipped, not `display:none`, so a screen reader in table-navigation mode still has real column headers) plus a `data-label` attribute on each `<td>`, restored as a `::before` label since visual column position no longer conveys meaning once rows stack. A `<td>` with no label (the row checkbox, the Details toggle) needed none — both are self-explanatory.
  - **Shared chart tooltip** (`components/charts/ChartTooltip.jsx`, `useChartTooltip`) for `LineChart`/`BarChart` — positioned from the hovered point/bar's own `getBoundingClientRect()` relative to the chart's container, not SVG viewBox math (which would misplace it on any chart not rendered at exactly 1:1 scale).
- **How the "keep it additive" and "keyboard focus" notes were actually resolved:**
  - **Additive, but not behind a new opt-in prop.** The original note ("a chart with no tooltip prop renders exactly as it does today") was read as a safety constraint, not a mandate for a permanently-optional feature: the existing native `<title>` is left completely untouched (same element, same content, zero risk to any existing test or behaviour), and the new HTML tooltip is purely additional. Since a nicer, faster, styled tooltip has no downside for any existing caller, it ships unconditionally rather than behind a prop nobody would ever choose to leave off — unlike drill-down (`onSelectPoint`/`onSelectBar`), which is a real behaviour change (a click now navigates somewhere) and genuinely needed to be opt-in.
  - **Keyboard focus, scoped to what's already focusable.** The tooltip fires on `mouseenter`/`mouseleave` for every point/bar, but `focus`/`blur` only on the ones that already carry `tabIndex={0}` — the drill-down-enabled ones. Making every decorative, non-interactive point additionally focusable just to attach a tooltip would add dozens of new Tab stops to a chart with no drill-down at all, a real keyboard-navigation regression in exchange for a purely informational feature. The acceptance criterion ("tooltips work by keyboard focus as well as hover") is satisfied for every element a keyboard user can actually already reach.
- **Tests:** 3 frontend (`App.test.jsx` — every group label present, every grouped page nested inside a `.nav-group`, Home/Alerts confirmed as the deliberate exceptions) + 2 (`TransactionsPage.test.jsx` — `.responsive-table` class and `data-label`s on both the plain and grouped tables) + 5 (`LineChart.test.jsx`/`BarChart.test.jsx` — tooltip shown on hover and hidden on mouseleave, shown on focus/hidden on blur for a clickable point/bar, and absent until interacted with). Full suites (699 backend, unaffected since this task is frontend-only; 712 frontend) green, lint and build clean.
- **Acceptance:** the nav groups every content-area destination with no orphans (Home/Alerts are the one deliberate, documented exception, not an oversight); the ledger is usable on a 375px viewport without horizontal scrolling; tooltips work by keyboard focus as well as hover, for every element that was already keyboard-reachable.

## Tier 3 — strategic

### T3.1 — Forecast scenarios

- **Status:** `[x]` — shipped in **0.29.0**.
- **Why:** the projection already exists (`services/forecast.py`); the unanswered question is "what if this subscription stops, or this category drops 20%".
- **What shipped:** `project()` gained two optional, independently-usable overlay parameters (`stopped_series_keys`, `category_adjustments`) - omitted by every existing caller, so the baseline projection is byte-for-byte unchanged. `services/forecast.category_daily_rates()` decomposes the exact same run-rate window `daily_run_rates()` already computes, per category, and `apply_category_adjustments()` folds a `{category_id: percent}` scenario into it - never a second, independently-computed rate. `POST /api/forecast/scenario` exposes both, returning the same `ForecastResponse` shape `GET /forecast` does. A new **Scenarios** card on `/forecast` lets a household check a recurring commitment to hypothetically stop, and/or pick a category + percent to adjust, then compares the result against the baseline directly on the same chart (baseline muted).
- **How the module's own load-bearing exclusion was protected:** a scenario-stopped series is deliberately NOT the same thing as a `RecurringDismissal` - it still counts toward the everyday-run-rate exclusion set (its past transactions genuinely were recurring and must stay out of the run rate), only its *future* occurrences in this one hypothetical projection are skipped. Conflating the two would have let a scenario silently double-count a stopped subscription's own history into the run rate the moment it was checked - exactly the double-counting bug the module's own docstring calls its most load-bearing property.
- **Scope note**: `category_daily_rates()` groups by `Transaction.category_id` directly, not `services.allocations`' allocation-aware view - a split transaction's allocated categories aren't reflected in a scenario's per-category breakdown. Documented as a deliberate approximation in both the module docstring and the README: a "what if" tool is inherently approximate, and pulling in allocation-level precision here would blur the "same query as the baseline" symmetry the exclusion rule depends on.
- **Tests:** 10 backend service-level (`test_forecast.py` - category rate isolation, recurring exclusion, uncategorized exclusion, the adjustment math, a stopped series not resurrecting into the run rate, a category adjustment moving the closing balance, and byte-for-byte no-scenario-params equality with the baseline) + 6 backend API-level (`test_forecast_api.py` - shape, defaults, stopping a series, a category adjustment, an unknown-category 404, an out-of-range-months 422) + 7 frontend (`ForecastPage.test.jsx` - the checkbox list, the disabled Run-scenario state, running each overlay kind, removing an adjustment row, clearing a scenario, and a scenario-request error). Full suites (715 backend, 719 frontend) green, lint and build clean.

### T3.2 — Rules v2 (multi-condition, regex)

- **Status:** `[x]` — shipped in **0.30.0**.
- **Why:** a rule's narration pattern is a single case-insensitive substring, which cannot express OR — which is exactly why the rule-review feature documents that "merge" can only mean "delete the rule that can never fire" (README's [Rule review](README.md#rule-review)).
- **What shipped:** `Category Rule.additional_patterns` (JSON, nullable) OR's extra narration patterns onto the existing `narration_pattern`, and `use_regex` switches every pattern (primary plus additional) from a substring check to a case-insensitive `re.search`. Both default to "off"/empty, so a rule using neither - every rule that existed before this - matches exactly as it always has; this is purely additive. `/rules` gained a repeatable **Also match (OR)** pattern list and a **Treat patterns as regular expressions** checkbox, plus a "regex" badge and the full OR'd pattern set shown in the rules table.
- **How the two "must keep working" constraints were actually resolved:**
  - **One matcher, still.** `services/categorization.py` gained exactly two new pure functions - `rule_patterns()` (collects narration_pattern + additional_patterns into one normalized list) and `narration_matches()` (substring-OR or regex-OR against that list) - and `criteria_match()`/`rule_matches()`/`preview_rule()` route through them instead of the old single-pattern check. Import, preview and apply all still call the identical function; the "preview said 12, apply did 9" class of bug the module's docstring warns about has exactly as little room to exist as before.
  - **Subsumption, generalized rather than rethought from scratch.** The roadmap's own note ("will need rethinking") turned out to have a clean answer: "earlier's pattern is a substring of later's" generalizes directly to two OR'd pattern SETS as "every one of later's own alternatives contains at least one of earlier's alternatives" - the same underlying containment relationship, just applied per-alternative. A REGEX rule (either side) is excluded from the analysis entirely rather than approximated, since containment between two arbitrary regexes isn't decidable in general and a wrong claim in either direction (a false "safe to remove", or a missed real duplicate) would be worse than no claim.
- **Tests:** 28 backend (`test_categorization.py` - pattern collection/normalization, OR matching, regex matching incl. case-insensitivity/unanchored search/invalid-regex-matches-nothing, and end-to-end apply-via-additional-pattern) + 15 (`test_rule_review.py` - full and partial multi-pattern coverage in both directions, a regex rule excluded as both the later and the blocking rule, and exact-duplicate set-equality regardless of pattern order) + 16 (`test_category_rules.py` - create/update/preview defaults, accepting valid patterns, rejecting an invalid regex in either the primary or an additional pattern, and previewing via an additional pattern) + 6 frontend (`RulesPage.test.jsx` - the joined-pattern + regex-badge display, adding/removing/submitting an alternative pattern row, a blank row omitted from the payload, and prefill on edit). Full suites (742 backend, 725 frontend) green, lint and build clean.

### T3.4 — Toast notifications

- **Status:** `[x]` — shipped in **0.32.0**. **Tier 3 is now complete.**
- **Why:** [Finding 15](#finding-15). Every action reports through inline text a user may never look at.
- **What shipped:** `services/toast.ts`, a module-level pub-sub store mirroring `subscribeToBuildIdentity`'s existing pattern (state lives outside React so any call site can fire a toast without being inside whatever component renders the container), plus a `<ToastContainer>` mounted once in `App.jsx` via `useSyncExternalStore`. `showToast(message, { tone, durationMs })` auto-dismisses after 4s by default (or never, with `durationMs: 0`), and is independently dismissible by its own button. Wired into a representative set of call sites - ledger import, a budget save, the Queensland preset, Apply rules now - each ADDITIVE to its existing inline message, never a replacement for it.
- **How the two constraints were actually resolved:**
  - **`prefers-reduced-motion`**: `.toast`'s fade/slide-in animation was added to the SAME existing media-query block every other animation in the app already opts out through (`.card-body`, `.modal`, `.skeleton-row`, ...) - one shared block, not a second one for toasts specifically.
  - **"Never the only place an error appears"**: resolved by scope, not by a rule that has to be remembered at every call site - `showToast()` is used ONLY for success confirmations across the whole codebase; no error path anywhere calls it. `<ErrorState>` remains the sole channel for anything a user needs to act on, exactly as before this task, which makes the constraint true by construction rather than by discipline.
  - **Exhaustive retrofit vs. representative wiring**: deliberately the latter. The roadmap's own two named examples (an import's count, a budget save) plus two more high-value ones (the Queensland preset, Apply rules now) are wired; touching every mutation in the app would have been a large, high-risk change for a purely additive confirmation. The infrastructure (`showToast()`) is a one-line addition anywhere else it's wanted later.
- **Tests:** frontend-only (no backend change) - 9 (`toast.test.js` - add/dismiss/auto-dismiss/custom-duration/never-dismiss/subscriber notification) + 7 (`ToastContainer.test.jsx` - empty render, a toast fired before vs. after mount, tone class, manual dismiss via its own button, multiple toasts at once, an external `dismissToast` call reflected live) + 4 (one new assertion each in `TransactionsPage.test.jsx`, `CategoriesPage.test.jsx` ×2, `RulesPage.test.jsx` confirming the exact toast text at each wired call site). ## Appendix A — review findings

Condensed from the full review of v0.22.1 on 2026-09-25. Kept here so each task's justification survives with it.

**What's already strong.** Single-source-of-truth resolution (`services/budgets.effective_budget`), one allocation view every money query reads through (`services/allocations.py`), presentation-edge filtering deliberately kept out of SQL, drill-down wired through every chart, a validated categorical chart palette with light/dark/auto theming, and real accessibility discipline (visually-hidden captions, `scope` attributes, keyboard-operable reordering rather than drag-only). The weaknesses below are not in the code's quality — they're in what the app won't let a household record, what it never tells them, and one conceptual gap in how budgets work.

#### Practice gaps

- <a id="finding-1"></a>**Finding 1 — No manual transaction entry.** `api/transactions.py` has import, bulk-categorize, split, note and delete, but no create. Cash spending and anything not yet on a statement are invisible. → [T1.1](#t11--manual-transaction-entry)
- <a id="finding-2"></a>**Finding 2 — Budgets don't carry over.** Per-month figures with overrides and no accumulation, so sinking funds (annual rego, insurance) are impossible to express. → [T2.1](#t21--budget-carryover-and-sinking-funds)
- <a id="finding-3"></a>**Finding 3 — Monthly-only budgeting against fortnightly pay.** Three months a year hold three pay cycles; a calendar-monthly budget mis-states them. → [T2.2](#t22--pay-period-budgeting)
- <a id="finding-4"></a>**Finding 4 — Nothing verifies the ledger is complete.** A missing statement silently understates every total. The stored running `Balance` column makes coverage *provable* rather than assumed — a capability few apps in this category have. → [T1.3](#t13--statement-continuity--coverage-check)
- <a id="finding-5"></a>**Finding 5 — Transfers aren't matched.** Each leg is categorized independently and nothing pairs them. → [T2.3](#t23--transfer-matching)
- <a id="finding-6"></a>**Finding 6 — No alerts; every signal is passive.** Price rises, missed bills and over-budget categories are computed but only found by visiting the right page. → [T2.4](#t24--alerts-feed)
- <a id="finding-7"></a>**Finding 7 — No savings rate, no runway.** The two standard household metrics, absent despite every input existing. → [T1.5](#t15--savings-rate-and-runway-tiles)
- <a id="finding-8"></a>**Finding 8 — Data goes in but never comes out.** No export of any kind. → [T1.4](#t14--csvjson-export)
